# API сервера задач: протокол 1, сервер 0.1.1

Адрес API: `PUBLIC_BASE_URL`. Полный список методов и схемы запросов находятся в [OpenAPI](openapi.json). Все UUID передаются в нижнем регистре. JSON — UTF-8; `Content-Type: application/json`. Файлы — `application/octet-stream`.

В защищённых запросах нужен `Authorization: Bearer ACCESS_TOKEN`. Идентификатор владельца определяется сервером по сессии. Локальные пути и идентификаторы EventKit в API не передаются.

## Регистрация и сессии

1. `POST /v1/auth/register`: `{email,password}` → `{challengeId,message}`. Пароль содержит 12–128 Unicode-символов.
2. Письмо содержит одноразовый 8-значный код. `POST /v1/auth/verify-email`: `{challengeId,code,password}`. Пароль передаётся повторно из формы регистрации и устанавливается только при подтверждении владения почтой; это защищает от предварительной регистрации чужого адреса.
3. `POST /v1/auth/login`: `{email,password,deviceId,deviceName}` → `{accessToken,refreshToken,expiresIn,sessionId,user}`. `deviceId` — постоянный UUID установки, `deviceName` — 1–100 символов.
4. `POST /v1/auth/refresh`: `{refreshToken}`. Старый refresh-токен становится недействительным; его повторное использование отзывает текущую сессию. Клиент выполняет refresh последовательно. Потеря ответа может потребовать повторного входа.
5. `POST /v1/auth/logout` отзывает текущую сессию; `GET /v1/devices` и `DELETE /v1/devices/{sessionId}` управляют устройствами.

`POST /v1/auth/resend-verification` принимает `{email}`. Восстановление: `/v1/auth/password-reset/request` с `{email}`, затем `/confirm` с `{challengeId,code,newPassword}`. После сброса нужен обычный вход, старые сессии отозваны. Код действует 10 минут, максимум 5 попыток; письма одному адресу не запрашиваются чаще раза в минуту.

`DELETE /v1/account` требует действующую сессию и `{password}`. Отзыв доступа немедленный, очистка рабочих данных выполняется worker.

## Первое подключение

`GET /v1/me` возвращает `libraryId`. `GET /v1/library` сообщает `initialized` и серверную `revision`. До первоначального commit обычные изменения отклоняются.

- `POST /v1/library/imports` с `{importId}` создаёт импорт на текущую сессию. Повтор с тем же ID безопасен.
- `POST /v1/library/imports/{id}/mutations` принимает пакет `{mutations:[...]}` только из операций `create`. Максимум 100 операций / 4 МиБ на запрос. Данные до commit не видны в рабочем снимке.
- `POST /v1/library/imports/{id}/commit` атомарно применяет импорт; папки создаются раньше задач, задачи раньше подзадач и вложений. Пустой импорт создаёт пустую библиотеку. Повтор commit безопасен.
- Если библиотека уже инициализирована, новый импорт её не заменяет. Клиент должен получить существующий снимок после согласованного с пользователем переключения.

## Изменения

`POST /v1/sync/mutations` получает пакет операций. Пример:

```json
{
  "mutations": [{
    "operationId": "11111111-1111-4111-8111-111111111111",
    "libraryId": "22222222-2222-4222-8222-222222222222",
    "deviceId": "33333333-3333-4333-8333-333333333333",
    "entityId": "44444444-4444-4444-8444-444444444444",
    "entityType": "task",
    "kind": "create",
    "changes": {
      "title": {"value":"Название", "version":{"physicalMillis":1793880000000,"logicalCounter":0,"deviceId":"33333333-3333-4333-8333-333333333333","operationId":"11111111-1111-4111-8111-111111111111"}},
      "createdAt": {"value":"2026-11-05T12:00:00.000Z", "version":{"physicalMillis":1793880000000,"logicalCounter":0,"deviceId":"33333333-3333-4333-8333-333333333333","operationId":"11111111-1111-4111-8111-111111111111"}},
      "placement": {"value":{"kind":"inbox"}, "version":{"physicalMillis":1793880000000,"logicalCounter":0,"deviceId":"33333333-3333-4333-8333-333333333333","operationId":"11111111-1111-4111-8111-111111111111"}}
    }
  }]
}
```

Идентификаторы примера заменяются фактическими. Метки правок создаются в момент локального сохранения. Метка не должна опережать сервер больше чем на 5 минут; при `clock_skew` клиент исправляет оценку времени и сохраняет очередь для корректного повторного действия.

Виды: `task`, `folder`, `checklistItem`, `attachment`. Операции: `create`, `update`, `delete`. Для удаления вместо `changes` нужен `deleteVersion` с той же структурой метки.

| Сущность | Поля |
|---|---|
| task | `title`, `description`, `createdAt`, `completedAt`, `focusDay`, `placement`, `deadline`, `planning` |
| folder | `name`, `sortOrder` |
| checklistItem | `taskId`, `title`, `isCompleted`, `sortOrder` |
| attachment | `taskId`, `filename`, `mimeType`, `size`, `sha256` |

Обязательны при создании: task — `title,createdAt,placement`; folder — `name,sortOrder`; подзадача — все поля её строки; вложение — все поля его строки. `createdAt` и `taskId` после создания не меняются. Вложения неизменяемы: для другого содержимого создаётся новое вложение.

`placement` — `{kind:"inbox"|"week"|"month"}` либо `{kind:"folder",folderId:UUID}`. `deadline` — `null`, `{includesTime:false,date:"YYYY-MM-DD",timeZoneId:"IANA"}` либо `{includesTime:true,instant:"UTC timestamp",timeZoneId:"IANA"}`. `planning` — `null` либо `{kind:"week"|"month",anchor:"UTC timestamp"}`. `focusDay` — дата или `null`; `completedAt` — момент UTC или `null`.

Название — до 16 КиБ UTF-8, описание — до 1 МиБ, имя папки — до 80 символов. Эти лимиты проверяются без молчаливого обрезания данных.

Метки сравниваются по `(physicalMillis,logicalCounter,deviceId,operationId)` обычным порядком чисел и ASCII-строк. Разные поля объединяются независимо. `placement` и `deadline` передаются как цельные поля. Повтор уже обработанного `operationId` возвращает прежний результат; другое тело с тем же ID даёт `operation_reused`.

Ответ `{results:[...]}` содержит статус каждой операции: `applied`, `deleted` или `rejected`. Успех включает актуальную `entity`; отклонение — стабильный код ошибки. Ошибки сервера/обслуживания возвращаются HTTP 503, пакет можно повторить с теми же ID. Результаты идемпотентности хранятся 90 дней.

Удаление имеет постоянный приоритет: обычное редактирование и повторное создание с удалённым UUID не восстанавливают сущность. Удаление задачи удаляет её дочерние сущности; удаление папки переносит задачи во «Входящие». Поздняя ссылка на удалённую папку нормализуется во «Входящие». Нормализация сохраняет исходную версию поля размещения, чтобы независимый перенос в другую папку сходился при любом порядке доставки. При одинаковой версии поля значение из более высокой серверной ревизии авторитетно; локальное поле с более новой неотправленной версией сохраняется до разрешения сервером.

## Получение состояния

`GET /v1/sync/snapshot` возвращает `{protocolVersion,libraryId,cursor,initialized,entities}` из одной согласованной транзакционной версии. Каждая сущность: `{id,type,fields,versions,deleted,revision}`; вложение дополнительно имеет серверный `fileReady`.

`GET /v1/sync/changes?cursor=...` возвращает `{libraryId,changes:[{revision,entity}],nextCursor,hasMore}`. Курсоры и серверные ревизии — десятичные строки. В одной странице до 100 записей. Сохраняйте изменения и `nextCursor` одной локальной транзакцией; продолжайте, пока `hasMore=true`.

Серверные изменения упорядочены по коммиту библиотеки. При `cursor_expired` (HTTP 410) нужен снимок с сохранением локальной исходящей очереди и её последующим наложением. Постоянные отметки удаления остаются и после очистки журнала.

## Файлы

1. Создайте задачу и сущность вложения обычными операциями синхронизации. SHA-256 — 64 шестнадцатеричных символа нижнего регистра. Пока нет байтов, `fileReady=false`.
2. `POST /v1/attachments/{id}/uploads` с `{uploadId}` → `{uploadId,ready,partBytes}`. Если одинаковые байты уже есть в этом аккаунте, сервер может сразу вернуть `ready=true`.
3. `GET /v1/uploads/{id}` сообщает принятые части и срок сессии.
4. `PUT /v1/uploads/{id}/parts/{index}` передаёт сырые байты. Индекс с нуля. Размер каждой части — 8 МиБ, последней — остаток. Повтор одинаковых байтов безопасен, отличающихся — `part_mismatch`.
5. `POST /v1/uploads/{id}/complete` проверяет весь файл. Для пустого файла частей нет, достаточно complete. Завершение идемпотентно.
6. `GET /v1/attachments/{id}/content` возвращает байты, исходное имя в `Content-Disposition` и `X-Content-SHA256`. Клиент проверяет сумму перед установкой файла в кэш.

Сессия живёт 24 часа, после истечения создаётся новая. Лимит файла 100 МиБ, общий начальный лимит 1 ГиБ. Дубликаты переиспользуются только внутри владельца. Запросы состояния/передачи/скачивания не дают доступ к чужим идентификаторам. `GET /v1/storage` показывает активные байты, резервы и удерживаемые удалённые объекты. Скачивание в первой версии возобновляется с начала; продолжение по частям относится к загрузке на сервер.

## Обслуживание и ошибки

`/health/live` проверяет процесс; `/health/ready` — БД, файловый каталог и отсутствие обслуживания. `/v1/config` сообщает лимиты и время сервера. Публичные методы не раскрывают параметры БД и SMTP.

Формат ошибки: `{error:{code,message,requestId}}`. Основные коды: `unauthorized`, `email_not_verified`, `rate_limited`, `invalid_code`, `registration_closed`, `clock_skew`, `missing_parent`, `operation_reused`, `cursor_expired`, `quota_exceeded`, `upload_expired`, `checksum_mismatch`, `maintenance`, `server_unavailable`.

Клиент использует коды, а не разбирает текст сообщения. При HTTP 429 учитывать `Retry-After`. При HTTP 429 `Retry-After` и дополнительное `error.retryAfterSeconds` содержат фактическое оставшееся число секунд. Это максимум для одновременно превышенных окон. Код `busy` означает занятые обработчики хеширования и короткое ожидание.

Заголовки клиента `X-Forwarded-For` принимаются только через явно настроенную доверенную цепочку прокси; IP не используется как удостоверение личности. Лимит защищённых запросов учитывается по подтверждённому аккаунту, refresh — по сессии, публичных запросов — по IP. Лимиты почты и авторизации по адресу остаются включёнными. Один запрос учитывается один раз, даже если маршрут повторно получает авторизованную личность.

OpenAPI 0.1.1 содержит именованные схемы ответов, ошибок, сущностей, меток версий и полей. `Mutation.changes.value` остаётся семантически зависимым от типа сущности и имени поля: схемы `TaskFields`, `FolderFields`, `ChecklistItemFields`, `AttachmentFields` задают значения. Неправильные значения отдельных операций возвращаются в `results`, сохраняя поведение протокола 1. Для удалённого неизвестного UUID `fields` может быть пустым. `fileReady` в ответе создания вложения может отсутствовать (считать `false`); в снимках он присутствует.
