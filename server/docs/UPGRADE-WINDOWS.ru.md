# Обновление Planner Server 0.1.0 → 0.1.1 на Windows

Цель — обновить существующий `C:\PlannerServer` на отдельном Windows-компьютере. Протокол остаётся версии 1. Структура SQL-таблиц не меняется; добавляются операторские значения в существующую таблицу `settings`. Рабочие тома `planner-server_database` и `planner-server_blobs`, аккаунты, UUID, секреты, открытая регистрация и публичный адрес сохраняются.

## Перед обновлением

1. Убедиться, что 0.1.0 отвечает `ready` и используется Compose-проект `planner-server`. Завершить другие операции обслуживания. Скрипт обновления поддерживает именно переход 0.1.0 → 0.1.1 и отказывается обновлять другой выпуск.
2. Выбрать отдельный резервный носитель. В **существующем** `C:\PlannerServer\config\server.env` заполнить `BACKUP_REPOSITORY_PATH`, например `E:/PlannerBackups`. Для сетевого диска он должен быть доступен текущему владельцу Windows. Сохранить `RESTIC_PASSWORD` отдельно в менеджере паролей. Не запускать инициализацию поверх существующей конфигурации.
3. Из старой установленной поставки выполнить `scripts\Backup-Server.ps1`, затем проверить `Restore-Server.ps1` в отдельном проекте. Проверить задачу и содержимое вложения. Рабочие тома не заменять тестовым восстановлением.
4. Скачать ZIP 0.1.1 **и отдельный файл `.zip.sha256`**. На Windows выполнить `Get-FileHash` для ZIP и сравнить со значением от отправителя. Внутренний манифест служит дополнительной проверкой, а не заменой независимой суммы архива.
5. Распаковать ZIP во временную папку, например `C:\PlannerUpdate\PlannerServer-0.1.1`. Новая `app` должна находиться **вне** текущей `C:\PlannerServer\app`.
6. Убрать необязательное закрепление `PLANNER_SERVER_VERSION` из `server.env` и текущего окружения PowerShell, если оно было добавлено вручную: версию выбирает Compose каждой поставки. Все прочие настройки сохранить. Убедиться, что есть доступ к npm/Docker Hub для сборки нового образа.

## Запуск обновления

Открыть PowerShell от того же владельца, который управляет Docker Desktop. После проверки ZIP разблокировать скачанные скрипты новой поставки и запустить обновление **из распакованной новой папки**:

```powershell
Set-Location C:\PlannerUpdate\PlannerServer-0.1.1\app
Get-ChildItem .\scripts\*.ps1 | Unblock-File
.\scripts\Update-Server.ps1 -InstallRoot C:\PlannerServer
```

При ограничении Execution Policy можно вызвать конкретный проверенный скрипт через `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ...`, сохраняя системную политику.

Обновление проверяет манифесты новой и установленной поставки, берёт блокировку операций, собирает образ 0.1.1 при работающем 0.1.0, делает новую копию старым скриптом и выполняет `restic check --read-data`. Без доступного, уже подготовленного репозитория обновление остановится. Затем предыдущие файлы сохраняются в `C:\PlannerServer\releases\0.1.0-<время>`, API и worker кратковременно останавливаются, заменяется только содержимое `app`, запускаются миграции, API и worker из локального образа. Успех требует ответа `ready` с версией `0.1.1`.

В этом переходе Compose использует тот же проект, тома и порты. Конфигурация, секреты, сторонние контейнеры и параметры Funnel не заменяются. Старый образ и резервная копия сохраняются.

При ошибке после замены файлов скрипт пытается вернуть прежние файлы и запустить образ 0.1.0. При сбое до замены рабочая поставка не заменяется. Результат находится в `logs\planner-server-update.json`; если автоматический откат не удался, следовать разделу аварийного возврата ниже.

## Приёмка 0.1.1

```powershell
Set-Location C:\PlannerServer\app
.\scripts\Get-ServerStatus.ps1
.\scripts\Test-Mail.ps1 -To "adevepstudio@yandex.ru"
.\scripts\Test-Proxy.ps1
```

`Get-ServerStatus` проверяет API локально и выводит операторские сведения: жив ли worker, очередь почты, безопасный код последней ошибки SMTP, последнюю копию и восстановление. Для имени отправителя можно задать в локальном `server.env` значение `MAIL_FROM='AlexDevep Studio <adevepstudio@yandex.ru>'`, сохранив `SMTP_USER` равным адресу ящика. После изменения выполнить `Start-Server.ps1`. Успешный SMTP-тест подтверждает отправку; получение письма и доставку кода проверяет владелец. `/health/ready` по-прежнему не является проверкой SMTP или резервной копии.

`Test-Proxy` создаёт временную диагностическую ссылку на 5 минут. Открыть её с двух внешних подключений, например мобильного интернета и другой сети. IP-адреса в публичный ответ не выводятся. Посмотреть результат локально:

```powershell
.\scripts\Test-Proxy.ps1 -Results
```

В `server.env` добавить `TRUSTED_PROXY_CIDRS` с **точным** `socketAddress` доверенного прокси, который видит контейнер. Это может быть адрес шлюза Docker, а не `127.0.0.1`. Не назначать всю частную сеть доверенной без проверки. Поддерживаются явные IP/CIDR; `true`, `*` и `/0` запрещены. Доверие распространяется только на контролируемый путь Tailscale → локальный порт Windows → Docker. Локальные процессы Windows входят в эту границу доверия. После изменения перезапустить и повторить тест:

```powershell
.\scripts\Start-Server.ps1
.\scripts\Test-Proxy.ps1
```

В результатах `clientAddress` должен различаться для разных внешних адресов. Подставленный скриптом `X-Forwarded-For: 203.0.113.123` должен быть перезаписан Tailscale фактическим адресом. Лимиты авторизованного API учитываются по проверенному аккаунту; публичные методы защищены ограничением по IP, авторизация дополнительно — по адресу почты, refresh — по сессии. Значения `USER_REQUESTS_PER_MINUTE` и `PUBLIC_REQUESTS_PER_MINUTE` по умолчанию 300. Пустой список прокси оставляет IP-защиту в консервативном режиме; несколько внешних клиентов в публичных методах могут делить лимит до настройки доверенного пути.

Проверить полный сценарий регистрации, подтверждения, входа, refresh и восстановления пароля на согласованном тестовом аккаунте. Проверить изоляцию двух аккаунтов и прежние задачи/вложения. Для проверки истечения лимита учитывать фактический `Retry-After`, а не постоянные 60 секунд.

## Копии и автоматизация

```powershell
.\scripts\Backup-Server.ps1 -FullCheck
.\scripts\Restore-Server.ps1 -Snapshot "ID_НОВОГО_СНИМКА"
```

Восстановление создаёт отдельный `planner-restore-*` с новым портом 13030; worker остановлен, прежние сессии отозваны, отложенные письма удалены. Проверить восстановленную задачу и SHA-256 вложения. Пароль шифрования и конфигурация хранятся отдельно от резервного репозитория; временный `backup-staging` резервной копией не является.

Успешное восстановление записывается в `logs\planner-restore-*-restore.json` и отображается в `lastRestoreTest` статуса основного сервера. После успешной проверки копии и восстановления установить задания:

```powershell
.\scripts\Install-ServerTasks.ps1 -BackupTime "03:00"
```

Время задаётся по часовому поясу Windows. Создаются только задания `PlannerServer-planner-server-Start` и `PlannerServer-planner-server-Backup` текущего владельца. Ежедневное копирование использует полную проверку данных. Задания работают при входе владельца, не хранят его пароль, пропущенный запуск догоняется после входа. Docker Desktop должен запускаться при входе; Resource Saver и автоматический сон от сети отключаются владельцем отдельно. Проверить перезагрузку, вход, блокировку экрана и внешний `/health/ready`.

Удаление собственных заданий: `Remove-ServerTasks.ps1`. Если перед возвратом на 0.1.0 задания уже созданы, удалить их: старый `Start-Server` выполняет сборку, а старый `Backup-Server` не знает параметр `-FullCheck`.

## Возврат после успешного обновления

Пока установлена 0.1.1, удалить задания, если они были созданы, и вызвать:

```powershell
.\scripts\Remove-ServerTasks.ps1
.\scripts\Rollback-Server.ps1 -PreviousApp "C:\PlannerServer\releases\0.1.0-ФАКТИЧЕСКОЕ_ВРЕМЯ"
```

Скрипт делает полную проверенную копию текущих данных, сохраняет файлы 0.1.1 и возвращает сохранённую 0.1.0. База и вложения сохраняют текущее содержимое: это возврат приложения, а не восстановление старой базы. Он допустим именно потому, что SQL-схема этого перехода не менялась. После возврата проверить локальный и внешний health, вход, задачи и файлы. Не удалять старые образы/выпуски до завершения приёмки.

Если файлы установленной `app` повреждены и скрипты не запускаются: сохранить их отдельно для диагностики, остановить только API/worker проекта `planner-server`, скопировать сохранённую `releases\0.1.0-...` в `app`, затем из неё выполнить `docker compose --project-name planner-server --env-file ..\config\server.env up -d --no-build --pull never --wait api worker`. Сохранить `config` и тома. Восстановление базы при действительном повреждении данных выполнять по проверенной процедуре в отдельный новый проект; не применять `down -v` к рабочему проекту.
