# План локального и облачного хранения и синхронизации

Зафиксировано 3 ноября 2026 года. План заменяет вариант синхронизации через личные Яндекс Диск и Google Drive. Это описание предстоящей реализации; текущая версия приложения продолжает хранить задачи локально.

## Состояние реализации на 5 ноября 2026 года

Подготовлена переносимая серверная поставка 0.1.0 для отдельного Windows-компьютера: API, SQL-миграции, почтовая очередь, файловое хранилище, Compose и скрипты резервного копирования и восстановления. Исходники — в `server/`, документация и результаты тестов входят в архив поставки. На целевом Windows сервер ещё не установлен; SMTP Яндекса и внешний HTTPS проверяются после переноса владельцем.

Интерфейс аккаунта, SwiftData V6, очередь изменений, синхронизация и вложения в клиенте macOS ещё предстоят. Ниже сохранён полный согласованный план, а не заявление о завершении всех его этапов.

## Серверная поставка 0.1.1, 6 ноября 2026 года

Работающий сервер 0.1.0 доступен по HTTPS; почта проверена владельцем Windows. Подготовлено совместимое обновление 0.1.1: схемы ответов API, доверенные прокси, отдельные лимиты аккаунтов, фактический Retry-After, операторская диагностика и скрипты обновления, возврата и автоматизации. Протокол остаётся 1; SQL-схема не меняется. Установка обновления и окончательная приёмка на Windows выполняются отдельно. Клиент macOS по-прежнему локальный.

## Принятые решения

Пользователь выбирает «Только на устройстве» или «Облачная синхронизация». Облачный режим использует единый сервер приложения и аккаунт пользователя. Локальная копия позволяет работать без интернета. Адрес сервера встроен в приложение; пользователь вводит только данные аккаунта.

| Вопрос | Решение |
|---|---|
| Начальное размещение сервера | Отдельный компьютер владельца с Windows 11 и 16 ГБ памяти, Docker Desktop и WSL2 |
| Публичный адрес | HTTPS через Tailscale Funnel; покупка домена и статический IP для первого запуска не требуются |
| Подключение клиентов | Обычный HTTPS, без установки VPN на телефоны и клиентские компьютеры |
| Вход | Почта и пароль, подтверждение почты и восстановление пароля через письма |
| Отправка писем | Отдельный технический ящик Яндекс Почты через SMTP |
| Последующая смена почты | Selectel SMTP после появления своего подтверждённого домена; аккаунты пользователей сохраняются |
| Конфликты | Побеждает последняя правка каждого поля; ручного разбора конфликтов нет |
| Вложения | Входят в первую реализацию, включая работу без интернета и загрузку на других устройствах |
| Первое подключение к существующей облачной библиотеке | После подтверждения использовать облачную библиотеку, предварительно сохранив локальную резервную копию |
| Шифрование | HTTPS при передаче; без сквозного шифрования в первой версии |
| Клиенты | Сейчас реализуется macOS; API и примеры формата готовятся для будущих Windows, iOS и Android |

Сервер обслуживает отдельные личные библиотеки разных аккаунтов. Общие задачи, приглашения в папки, тарифы, платежи и внешние облачные диски в первую версию не входят.

## Текущая основа приложения

Приложение использует Swift, SwiftUI, AppKit и SwiftData. Рабочая библиотека находится в sandbox-контейнере, схема — V5. Пользовательские изменения сохраняет `TaskService`, автоматическое сохранение контекста отключено. Задачи, папки и подзадачи уже имеют UUID. Системные события обслуживаются EventKit; напоминания о сроках — локальным сервисом уведомлений.

Схемы V1–V5 остаются неизменными. При реализации вводится V6 с миграцией существующей библиотеки. Bundle ID рабочего приложения сохраняется. Существующие несвязанные исправления календаря и уведомлений необходимо сохранить.

## Режимы хранения

### Только на устройстве

- Это режим по умолчанию для существующих пользователей и новых установок.
- Аккаунт не нужен. Содержимое задач и вложений не отправляется на сервер; опрос сервера синхронизации не запускается.
- Доступны задачи, папки, сроки, уведомления и локальные вложения. Возможность подключить системный календарь сохраняется независимо от режима.
- Локальная библиотека и облачные кэши разных аккаунтов хранятся отдельно.

### Облачная синхронизация

- Пользователь входит в аккаунт и подключает его библиотеку.
- Чтение и редактирование используют локальную базу. Каждая успешно сохранённая правка попадает в устойчивую очередь отправки.
- Состояние «сохранено на устройстве» отличается от «принято сервером». Недоступный сервер не препятствует локальному сохранению.
- Метаданные задач и передачи вложений имеют отдельные очереди и статусы.
- Сроки синхронизируются; разрешения уведомлений, ежедневное напоминание, язык, геометрия окна и выбор календарей остаются настройками устройства.

### Подключение и переключение режимов

1. Если серверная библиотека пуста, предложить загрузить текущую локальную библиотеку или начать пустую. Без выбора загрузка не начинается. Начальную загрузку выполнять в отдельную серверную сессию импорта; данные становятся рабочей библиотекой только после успешного завершения импорта.
2. Если библиотека на сервере существует, показать аккаунт и предупреждение о замене локальной рабочей библиотеки. Создать логический резервный архив, загрузить и проверить серверный снимок во временное хранилище, затем переключить библиотеку. При любой ошибке текущая библиотека остаётся активной. Неотправленные данные другой библиотеки в серверную автоматически не объединять.
3. Архив содержит задачи, папки, подзадачи, локальные календарные связи, сведения о вложениях и доступные локальные файлы. Недоступные локально файлы обозначаются в манифесте; архив не называется полной копией этих файлов. Архив можно открыть отдельной локальной библиотекой без автоматического подключения к облаку.
4. «Перейти к локальному хранению» сначала получает актуальные данные и все недостающие вложения, сохраняет копию с новым локальным идентификатором библиотеки и отключает обмен. Если сервер недоступен или скачивание не закончено, полный переход не завершается. Отдельно разрешить экспорт уже доступных данных с явным списком недостающих файлов.
5. Выход из аккаунта и удаление данных с сервера — разные действия. При выходе предложить сохранить полную локальную копию либо удалить кэш аккаунта; при неотправленных изменениях по умолчанию отменять выход и показывать их количество. Не выполнять удаление или переключение молча.
6. При смене аккаунта остановить обработчики, очистить учётные данные сессии и открыть отдельное хранилище нового аккаунта. Прежние очередь и кэш не пересылаются другому владельцу.

## Серверная архитектура

Использовать один модульный backend в этом репозитории, а не набор микросервисов. Технические значения ниже — исходные настройки первой реализации; они не означают уже установленное ПО.

| Компонент | Выбор |
|---|---|
| Runtime | Node.js 24 LTS внутри контейнера, TypeScript |
| HTTP API | Fastify 5, JSON Schema для проверки запросов и OpenAPI для контракта |
| База | PostgreSQL 18, SQL-миграции и параметризованные запросы через `pg` |
| Вложения | Приватный постоянный Docker volume с файлами, доступными только через API |
| Долгие задачи | Очередь заданий в PostgreSQL и отдельный worker из того же образа |
| Почта | SMTP через Nodemailer; локальный тестовый профиль с Mailpit |
| Доставка | Docker Compose для API, worker и PostgreSQL; Tailscale работает на Windows-хосте |

Точные поддерживаемые patch-версии зависимостей и образы фиксировать lock-файлом и версиями образов при реализации. [Политика поддержки Node.js](https://nodejs.org/en/about/previous-releases), [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/).

Выделить модули `auth`, `libraries`, `sync`, `attachments`, `mail` и `operations`. Рабочие процессы используют одну базу и общий интерфейс `BlobStore`. В первой версии реализуется файловый `BlobStore`; переход на S3-совместимое хранилище позднее не меняет клиентский API.

Основные серверные сущности: пользователи, устройства и сессии, библиотека, папки, задачи, подзадачи, вложения и объекты файлов, версии полей, отметки удаления, журнал изменений, результаты обработанных операций, сессии загрузки и задания worker. У каждой принадлежащей пользователю записи есть владелец и библиотека.

Владельца определять из сессии. Запросы не получают право доступа из присланного `userId`. Проверка владельца обязательна также для скачивания, частей файла, завершения загрузки, снимков и удаления аккаунта. База и файловые volume не публикуются в интернет.

## Аккаунты и восстановление доступа

- Регистрация: почта, пароль, письмо с подтверждением. До подтверждения не разрешать загрузку пользовательской библиотеки. В первом домашнем пилоте разрешать регистрацию только для списка тестовых адресов; публичное открытие регистрации — отдельная настройка владельца сервера.
- Пароль: от 12 до 128 символов, без обязательных наборов спецсимволов; не обрезать и не изменять введённое значение. Хранить Argon2id-хэш с индивидуальной солью, исходная конфигурация — 64 МиБ, 3 прохода, параллелизм 1. Проверить стоимость хэширования на сервере и ограничить одновременные операции авторизации. [OWASP о хранении паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Для подтверждения почты и сброса пароля использовать одноразовый 8-значный код, срок 10 минут, максимум 5 попыток на запрос. В базе хранить защищённое представление кода, а не исходное значение. Повторная отправка — не чаще раза в минуту и не более 5 раз в час на адрес; дополнительно ограничить запросы по IP. Новый запрос не обнуляет общий счётчик ограничений.
- Сброс пароля выполняется внутри приложения по коду из письма, затем нужен обычный вход. Ответ на запрос восстановления одинаков для существующего и неизвестного адреса. После смены пароля отзывать все сессии. [OWASP о восстановлении паролей](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- Выдавать случайные access- и refresh-токены; в базе хранить их хэши. Access действует 15 минут, refresh — до 30 дней бездействия и не дольше 90 дней после входа. Refresh ротируется; повтор использованного токена отзывает сессию устройства. Клиент выполняет обновление токена одним обработчиком. При утрате ответа на обновление допустим повторный вход, без ослабления проверки повторного использования.
- На macOS хранить refresh-токен в Связке ключей, access — в памяти; пароль не сохранять. В настройках доступны список устройств и отзыв сессии. Выход отзывает текущую сессию, если сервер доступен, и очищает локальные токены.
- Письма содержат только назначение операции, код и срок действия. Названия задач, вложения, пароли и токены в почту и журналы не включаются. Сбой SMTP не затрагивает сохранённые задачи и действующие сессии.

## API первой версии

Префикс API — `/v1`. Формат — JSON UTF-8; файлы передаются отдельно. Клиентские ошибки имеют стабильный код, понятное сообщение и `requestId`. Контракт и примеры для будущих клиентов поставляются вместе с сервером.

| Группа | Методы и назначение |
|---|---|
| Конфигурация | `GET /v1/config` — версия протокола, время сервера, доступность регистрации и лимиты |
| Регистрация | `POST /v1/auth/register`, `/verify-email`, `/resend-verification` |
| Сессия | `POST /v1/auth/login`, `/refresh`, `/logout` |
| Пароль | `POST /v1/auth/password-reset/request`, `/confirm` |
| Аккаунт | `GET /v1/me`, `GET /v1/devices`, `DELETE /v1/devices/{id}`, `DELETE /v1/account` |
| Первое подключение | `GET /v1/library`, `POST /v1/library/imports`, загрузка пакетов импорта и `POST /v1/library/imports/{id}/commit` |
| Синхронизация | `GET /v1/sync/snapshot`, `GET /v1/sync/changes?cursor=...`, `POST /v1/sync/mutations` |
| Вложения | Создание сессии загрузки, получение её состояния, `PUT` частей, завершение; `GET /v1/attachments/{id}/content` |
| Обслуживание | `/health/live`, `/health/ready`; защищённые административные команды вне публичного пользовательского API |

Изменения задач и метаданных вложений проходят через единый протокол синхронизации. Загрузка байтов файла завершается отдельной серверной операцией. Повторные запросы импорта, операций и завершения файла должны возвращать прежний результат, а не создавать новые сущности.

## Протокол синхронизации

### Идентификаторы и версии

Зафиксировать `protocolVersion=1`, JSON Schema и эталонные примеры. UUID — строки; даты и моменты времени — явно разные типы: `YYYY-MM-DD` для календарных дней, RFC 3339 UTC для моментов. Часовой пояс срока хранится отдельно. Пустое поле и `null` имеют разные значения: отсутствие поля означает «не менять», `null` — «очистить».

Каждая операция содержит `operationId`, `deviceId`, `libraryId`, тип сущности, UUID сущности, вид `create/update/delete` и изменённые поля с их версиями. Все поля версии используют переносимые целые числа и строки, без типов SwiftData. Версия поля — упорядоченная метка `(physicalMillis, logicalCounter, deviceId, operationId)`; сравнение одинаково описано для всех языков.

Клиенты используют время сервера для оценки смещения часов и сохраняют монотонную последовательность собственных меток. При получении удалённой версии обновляют логические часы: следующая локальная правка должна быть новее уже наблюдавшейся версии. Доставка старой офлайн-правки позже новой не делает старую победителем. Для независимых офлайн-правок истинный порядок зависит от точности часов устройств; при обнаруженном расхождении более 5 минут клиент показывает предупреждение. Нельзя выдавать порядок получения запросов за время пользовательской правки.

### Поля и связи

- Независимо объединяются название, описание, выполнение, отметка «Сегодня» и отдельные поля подзадачи. Имя и порядок папки имеют собственные версии.
- Основная папка задачи передаётся одной ссылкой на пользовательскую папку либо системную папку; её части не объединяются независимо.
- Срок — одна согласованная группа: дата/момент, наличие времени и часовой пояс. Прежние поля планирования также передаются согласованно.
- Сервер применяет только более новую версию поля и возвращает фактически принятое состояние. Устаревшая правка считается обработанной; клиент принимает серверное значение без окна конфликта.
- Связи проверяются в пределах владельца и библиотеки. При перестановках с одинаковым порядком использовать UUID как стабильное дополнительное сравнение. Разные папки с одинаковым именем не склеивать и не удалять автоматически.
- EventKit-идентификаторы, права, локальные пути, состояние загрузки кэша и настройки устройства не входят в DTO синхронизации. В резервном локальном архиве календарные связи сохраняются.

### Очередь и журнал

1. Изменение модели, версии полей и запись в локальную очередь сохраняются одной транзакцией. Это относится также к созданию и удалению папок и подзадач. Неуспешные черновики в очередь не попадают.
2. Очередь разделяется по аккаунту, библиотеке и устройству. Отправка откладывается на 2 секунды после правки; последовательные неотправленные изменения одного поля можно объединять, сохраняя последнюю версию. Опубликованная операция не меняет свой `operationId` и тело.
3. Сервер обрабатывает пакет до 100 операций и 4 МиБ. Каждая операция атомарна; результат содержит её статус и актуальные значения. Успех записи, запись результата идемпотентности и изменение журнала коммитятся вместе.
4. Серверный номер изменения выделять под блокировкой строки библиотеки в той же транзакции. Это обеспечивает порядок коммитов; обычный `serial` сам по себе не является курсором порядка коммита. [Свойства транзакций и последовательностей PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).
5. Чтение журнала возвращает страницы с ограниченным размером и курсор. Клиент сохраняет полученные изменения и новый курсор одной транзакцией. Повторная доставка безопасна. Снимок содержит согласованное состояние и водораздел журнала из одной транзакционной версии базы.
6. При устаревшем курсоре сервер возвращает `cursor_expired`. Клиент сохраняет очередь, получает новый снимок во временную базу, повторно накладывает свои ещё не отправленные изменения и продолжает обмен. Первоначальная замена библиотеки и обычное восстановление курсора — разные операции.

Опрос — раз в 60 секунд в активном приложении, а также при запуске, активации, восстановлении сети и ручной команде. Один обработчик синхронизации на библиотеку. Повторы с увеличением интервала и случайной добавкой, максимум 5 минут; учитывать `Retry-After`. При повторной авторизации и восстановлении соединения очередь сохраняется.

### Удаления и длительное отсутствие устройства

Удаления представлены постоянными компактными отметками с UUID и владельцем. Обычный `update` не восстанавливает удалённую сущность, а повторный `create` с удалённым UUID отклоняется. Восстановленная из архива сущность получает новый UUID с согласованным переназначением ссылок её подзадач и вложений.

Удаление папки переводит её задачи во «Входящие». Сервер не принимает позднюю ссылку на удалённую папку. Удаление задачи закрывает её подзадачи и вложения независимо от порядка их доставки. Клиент показывает серверное состояние вместо повторной бесконечной отправки таких операций.

Журнал и результаты операций хранить 90 дней; компактные отметки удаления — весь срок существования библиотеки. Старое устройство проходит полную пересинхронизацию. Удаление аккаунта блокирует сессии и загрузки сразу, запускает удаление рабочих данных в течение 24 часов; прежние зашифрованные резервные копии истекают по сроку хранения, максимум 30 дней.

## Вложения

### Пользовательское поведение

- Блок «Вложения» в карточке: кнопка добавления, перетаскивание, имя, размер, прогресс, повтор передачи, просмотр, сохранение копии и удаление.
- Добавление копирует файл в приватную библиотеку; перемещение исходника не влияет на вложение. Импорт доступен и в локальном режиме.
- Принимаются обычные файлы до 100 МиБ. Каталоги, пакеты приложений и символические ссылки не принимаются. Исходное имя не используется как путь хранения.
- На другом устройстве сразу видна информация о файле; содержимое скачивается при запросе. Предусмотреть настройку «Хранить все вложения на этом устройстве», по умолчанию выключенную.
- Просмотр — Quick Look, сохранение копии — системный диалог. Редактирование содержимого внешним приложением в первую версию не входит.

### Хранение и передача

Метаданные: UUID вложения и задачи, исходное имя, тип, размер, SHA-256, дата добавления и ссылка на серверный объект. Признак готовности серверного файла изменяет сервер, а наличие локальной копии хранится только на устройстве.

Начальный лимит облачных файлов — 1 ГиБ на аккаунт, настраиваемый владельцем сервера. Дополнительно резервировать место под начатые загрузки. Одинаковые байты допускают переиспользование объекта только внутри одного аккаунта. Информация о совпадениях между разными пользователями не раскрывается.

Сначала синхронизируются задача и метаданные вложения, затем передаются байты. На другом устройстве незавершённый файл имеет статус «Ожидает загрузки с другого устройства». Текст задачи и другие вложения продолжают синхронизироваться независимо.

Файл загружается частями до 8 МиБ через API с авторизацией. Сессия привязана к владельцу, вложению и ожидаемым размеру и SHA-256. Повтор одинаковой части идемпотентен; несовпадающая часть с тем же номером отклоняется. После обрыва клиент запрашивает уже принятые части. Максимум две параллельные передачи на клиенте.

Завершение проверяет весь размер и SHA-256, атомарно помещает файл в постоянное хранилище и публикует состояние готовности. Перед завершением повторно проверить, что задача и вложение не удалены. Повтор завершения возвращает тот же результат. Брошенные сессии очищаются через 24 часа; клиент может создать новую сессию для того же живого вложения.

Скачивание идёт во временный файл с проверкой контрольной суммы и последующим атомарным переносом в кэш. Очистка кэша удаляет только подтверждённо доступные на сервере копии; локальные и неотправленные оригиналы сохраняются.

После удаления последней ссылки сервер удерживает объект 30 дней, затем worker удаляет его. Метаданные удаления сохраняются. Удерживаемые объекты занимают место; настройки показывают активные файлы, резерв загрузок и ожидающие очистки объекты раздельно. Перед исчерпанием места показывать понятное состояние, не удаляя неотправленные файлы.

## Интеграция в macOS

- Ввести `StorageMode`, `AccountSession`, `SyncEngine`, `SyncTransport`, `SyncRepository`, `AttachmentService` и наблюдаемое состояние обмена. Контрактные DTO отделить от SwiftData и UI.
- В схеме V6 добавить вложения, версии полей, очередь, курсоры и идентичность библиотек. Миграция сохраняет текущие UUID, даты, папки и календарные связи. Локальный режим после обновления включён по умолчанию.
- Перевести все сохранения синхронизируемых сущностей в общий механизм транзакции. Получение удалённых данных не создаёт исходящие операции.
- Дополнить настройки разделом «Хранение и синхронизация»: режим, аккаунт, вход, регистрация, подтверждение почты, восстановление пароля, устройства, объём файлов, экспорт и переход к локальному режиму.
- Показывать «Сохранено на устройстве», «Ожидает соединения», «Синхронизировано», «Требуется вход» и ошибки отдельных файлов. Сбой сервера не показывать как ошибку локального сохранения.
- Защитить активный редактор: фоновые значения не подменяют текст с текущим вводом или IME-композицией. Применять отложенное значение после завершения редактирования с учётом версии последней локальной правки. Регрессионно проверить курсор, выделение, Undo и многострочные подзадачи.
- После удалённого изменения названия, срока, выполнения или удаления пересчитать локальные уведомления через существующий сервис. Не перезаписывать его обработчики и не запрашивать разрешения повторно.
- Добавить sandbox-права исходящих соединений и работы с выбранными файлами; изменения отразить в генераторе Xcode и проверках упаковщика. Разрешение системного календаря остаётся независимым.
- Добавить RU/EN-переводы. При выпуске обновить описание конфиденциальности и текущие ограничения: только выбранный облачный режим передаёт задачи владельцу сервера; сквозного шифрования нет.

## Домашний сервер Windows и постоянный адрес

Подготовка владельцем описана отдельно в [инструкции Windows](windows-server-setup.ru.md). Компьютер использует Windows 11, 16 ГБ памяти, WSL2 и Linux-контейнеры Docker Desktop. API публикуется только на `127.0.0.1:3030`, PostgreSQL не публикует порт. Tailscale Funnel пересылает публичный HTTPS только в API, а не в папки компьютера или Docker API.

Для первого пилота использовать стабильный адрес `https://<имя-устройства>.<имя-сети>.ts.net`. Покупка домена, проброс входящих портов и установка Tailscale на клиентские устройства не требуются. Адрес зависит от сохранения аккаунта, имени устройства и DNS-имени сети. Funnel находится в beta и имеет ограничения полосы; это ограничение домашнего пилота, не гарантия постоянной доступности. [Возможности Funnel](https://tailscale.com/docs/use-cases/application-testing/share-local-dev-server-with-internet), [ограничения](https://tailscale.com/docs/features/tailscale-funnel).

Точный полученный адрес записать в конфигурацию сборки, не придумывать его заранее. Локальные тесты используют отдельный HTTP-адрес в тестовой конфигурации; Release принимает только HTTPS. Смена адреса требует выпуска с обновлённой конфигурацией, поэтому серверное имя после подключения клиентов не менять.

Сервисы Compose имеют healthcheck и `restart: unless-stopped`. Docker Desktop запускается при входе пользователя Windows; планировщик после входа ожидает готовности Docker и выполняет запуск Compose. После перезагрузки до входа пользователя доступность не обещается. Автоматический вход с сохранением пароля не настраивать. Проверить остановку, повторный вход, блокировку экрана и восстановление Funnel. [Настройки автозапуска Docker](https://docs.docker.com/desktop/settings-and-maintenance/settings/), [возобновление Funnel с `--bg`](https://tailscale.com/docs/reference/tailscale-cli/funnel).

Владелец настраивает питание так, чтобы компьютер не засыпал во время обслуживания. Выключение, сон, отсутствие интернета и остановка Docker переводят клиенты в офлайн-режим; они не теряют локальные изменения. Круглосуточный сервис без участия владельца потребует последующего перехода на постоянно работающий хост.

## Почта и конфигурация

Создать отдельный технический ящик Яндекс Почты и пароль приложения для SMTP. Начальные параметры: `smtp.yandex.ru`, порт `465`, TLS с начала соединения, логин и адрес отправителя — полный адрес технического ящика. Доступ почтовых клиентов и паролей приложений включается по настройкам ящика. [Настройка Яндекс Почты](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others.html), [пароли приложений](https://yandex.ru/support/id/ru/authorization/app-passwords).

SMTP-провайдер задаётся конфигурацией, а не кодом авторизации. Selectel можно подключить позднее: для него нужен свой домен с проверочными TXT, SPF, DKIM и DMARC; домен Funnel для этого не используется. [Инструкция Selectel](https://docs.selectel.ru/email-service/connect-email-service/).

В поставку сервера входят `compose.yaml`, пример конфигурации без секретов и PowerShell-скрипты `Start-Server`, `Stop-Server`, `Get-ServerStatus`, `Test-Mail`, `Backup-Server` и `Restore-Server`. Команды и имена скриптов в этом разделе описывают результат реализации, а не уже существующие файлы.

Конфигурация включает `PUBLIC_BASE_URL`, параметры PostgreSQL, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, `ALLOWED_REGISTRATION_EMAILS`, лимиты хранения и путь резервных копий. Секреты находятся на Windows-сервере в защищённом конфигурационном каталоге вне Git; исходники, приложение, архивы диагностики и сообщения чата их не содержат.

## Резервные копии и обслуживание

- Ежедневно создавать согласованный `pg_dump`, манифест и копию файлов; удерживать физическое удаление объектов на время копирования. Новые недопринятые загрузки в копию не включать. Раз в неделю проверять восстановление последней копии в отдельный тестовый Compose-проект.
- Хранить последние 7 ежедневных и 4 еженедельных комплекта, не дольше 30 дней. Полный комплект включает файл версии сервера и подтверждённые SHA-256 объектов. Копии защищать шифрованием; ключ хранить отдельно от архивов.
- Владелец предоставляет отдельный носитель или второй компьютер для копий. Второй каталог на системном диске не считать защитой от отказа компьютера. До первого хранения важных облачных данных проверить такую копию и восстановление.
- Обновление сервера: резервная копия, остановка записи, миграция, запуск, проверка готовности и контрольный обмен двух клиентов. Откат несовместимой миграции выполняется восстановлением согласованного комплекта, а не простым запуском старого образа.
- Серверные логи содержат request ID, коды ошибок, длительности и технические идентификаторы. Тексты задач, тела писем, пароли и токены исключены. Для диагностики нужны состояние Docker, готовность БД, свободное место, возраст резервной копии, очередь почты и ошибки передач.
- Плановые задания выполняются worker с блокировками в PostgreSQL, чтобы повтор запуска не дублировал письма или очистку. Общую скорость писем ограничить конфигурацией SMTP-провайдера.
- На домашнем пилоте нет SLA. Для приглашения пользователей вне пилота сначала проверить доступность, лимиты, резервное восстановление и обновлённое описание конфиденциальности.

## Этапы реализации и результаты

| Этап | Работа | Критерий завершения |
|---|---|---|
| 1. Контракт | OpenAPI, JSON Schema, правила версий полей, ошибки, эталонные данные, ограничения | Примеры разбирают Swift и независимый Python-проверяющий; платформенных идентификаторов в обмене нет |
| 2. Серверная основа | Docker Compose, PostgreSQL, миграции, аккаунты, SMTP, сессии, проверки владельца | Регистрация, подтверждение и восстановление проходят; второй пользователь не получает чужие данные |
| 3. Обмен | Журнал, снимки, операции, удаления и курсоры; два поддельных клиента | Изменения сходятся при разных порядках доставки, повторах и отключениях |
| 4. Клиент macOS | V6, очередь, переключение библиотек, авторизация, настройки, уведомления и редакторы | Два изолированных экземпляра обмениваются задачами; локальный режим работает без сервера |
| 5. Вложения | Импорт, просмотр, части файлов, квота, кэш, повторы и очистка | Файл после обрыва догружается без повторного создания; права и суммы проверены |
| 6. Windows-пилот | Запуск, Funnel, реальная почта, резервные копии и восстановление | Mac подключается из внешней сети; сервис возвращается после перезагрузки и входа владельца |
| 7. Выпуск | Регрессионные проверки, RU/EN-документы, конфиденциальность, универсальный macOS DMG | Указаны фактические результаты проверок; версия и SHA-256 пакета проверены |

Будущие приложения Windows, iOS и Android реализуются отдельными задачами по опубликованному контракту. Docker на Windows здесь нужен для сервера и не означает, что уже создан Windows-клиент задач.

## Проверки и приёмка

- Миграция V1–V5 → V6: сохранены UUID, текст, вложенные связи, даты, сроки и локальный режим. Ошибка миграции не подменяет библиотеку пустой.
- Локальный режим: сервер выключен, аккаунта нет, сетевой обмен библиотеки не начинается; добавление, редактирование и вложения работают.
- Авторизация: неверный пароль, неподтверждённая почта, просроченный и повторный код, ограничения запросов, сброс пароля, отзыв сессии и изоляция двух владельцев.
- Синхронизация: разные поля одной задачи, несколько правок одного поля, одинаковые часы, неверные часы, доставка в обратном порядке, повтор операции, потерянный ответ после коммита, перезапуск с очередью и несколько страниц журнала.
- Удаления: офлайн-правка удалённой задачи, удаление папки одновременно с переносом задачи, удаление задачи во время передачи вложения, устаревший курсор и повторный снимок. Удалённые сущности не возвращаются.
- Режимы и аккаунты: пустой сервер, существующая библиотека, неуспешный архив или снимок, неподтверждённая замена, незавершённый начальный импорт, переход к полной локальной копии, выход с очередью и смена аккаунта.
- Файлы: 0 байт, несколько одинаковых имён, повтор байтов, 100 МиБ и превышение, запрещённые типы файлов, неверный SHA-256, отсутствующая часть, повтор части с другими байтами, истечение загрузки, квота и переполнение диска.
- UI: состояния обмена отдельно от сохранения, активация окна, редактор с IME, ввод в середине текста, Undo, выделение при потере фокуса, подзадачи, закрытый раздел выполненных и корректировка уведомлений.
- Windows: исходящий HTTPS-туннель, работа за домашним NAT, доступ из внешней сети без клиентского VPN, сон и пробуждение, перезапуск Docker, вход после перезагрузки Windows и сохранение адреса.
- Эксплуатация: реальные письма регистрации и восстановления, согласованная резервная копия и восстановление на чистом Compose-проекте, недоступный SMTP, отключение сети и повторный запуск worker.

Автоматические проверки используют временные базы, файловые каталоги, тестовые аккаунты и подмену календаря/уведомлений. Реальный публичный адрес и SMTP проверяются отдельно после подготовки Windows-сервера владельцем. Текущая серверная поставка проверяется в изолированных временных контейнерах на Mac. Эти контейнеры не являются рабочим сервером; установка выполняется отдельно на Windows. Приложение macOS этим этапом не изменяется.
